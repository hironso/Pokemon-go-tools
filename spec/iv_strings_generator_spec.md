## 1. 概要

ポケモンGOのボックス整理用検索キーワードを自動生成するStreamlitアプリ。
`iv_list_input.txt`をアップロードすると、SCPランキングをもとにバケット単位の検索式を生成して`iv_list_output.txt`として出力する。

- **デプロイ先**: Streamlit Community Cloud
- **メインファイル**: `iv_strings_generator/app.py`
- **参照ファイル**（形式は各データファイル spec を参照。5章・11章）:
  - `pokedex_numbers.txt`（図鑑番号・種族値の辞書。形式は `pokedex_numbers_spec.md`）
  - `evolution_map.txt`（進化ファミリーの辞書。形式は `evolution_map_spec.md`）
  - `slim_cache.json`（SCPランキングの軽量キャッシュ。形式は `slim_cache_spec.md`）
  - `iv_list_input_templete.txt`（入力テンプレート）

このアプリの処理は大きく次の順序で進む。本仕様書もこの順に章立てする。

1. 入力を読み、対象ポケモン×リーグ（ユニット）を確定する（3章）。
2. 各ファミリーについて、SCPランキングから採用バケットを決める（6章。**本改訂で変更しない**）。
3. 決まったユニットを27パターンへ割り当て、丸めて各グループが有効閾値以上になるよう集約する（7・8章。**本改訂の中心**）。
4. グループごとに検索式を組み立てて出力する（9章）。

> **本改訂（Rev1.1）で変わるのは「グループ分けおよびそれ以降の集約・出力」だけである。**
> 入力の解釈（3章）は、O/M/L展開の分岐対応（3章のルール明確化）を除き、変更しない。ファミリーのIV決定ロジック（6章）は変更しない。

## 2. 用語定義

本書では、同じ対象を常に同じ語で表す。グループ分けに関する章（7章以降）はすべてこの用語に従う。

| 用語 | 定義 |
|---|---|
| **バケット** | IV を 5 段階（0〜4）に量子化した値。詳細は4章。0=IV0, 1=IV1〜5, 2=IV6〜10, 3=IV11〜14, 4=IV15。 |
| **軸** | こうげき・ぼうぎょ・HP の 3 つのいずれか。 |
| **パターン** | 検索条件の 1 定義。こうげき上限 `a`、ぼうぎょ下限 `d`、HP下限 `h` の 3 値で表す。<br>こうげき = バケット `{0..a}`、ぼうぎょ = バケット `{d..4}`、HP = バケット `{h..4}`。<br>**パターンは「定義」であり、中身（ユニット）が入っているとは限らない。** |
| **ユニット** | ポケモン × リーグ を進化ファミリー単位にまとめた 1 件（FamilyUnit）。割り当て・丸めの最小単位。<br>同一ファミリー（同一の図鑑番号集合）に属するリクエストは、各軸のバケット要求を軸ごとに和を取って 1 ユニットにまとめる。 |
| **総ユニット数** | 入力（iv_list_input.txt）から構築した全ユニット（FamilyUnit）の件数。個別枠に落ちるユニットも含む。<br>出力ヘッダーの「ユニット数：N」と同じ値。**丸め込み中は変化しない固定値**。 |
| **グループ** | あるパターンにユニットが 1 件以上割り当てられた実体。<br>**「パターン」は定義、「グループ」は中身入り**、と区別する。 |
| **グループのユニット数** | あるグループに割り当てられているユニットの件数。<br>**丸め（8章）の大きさ判定・閾値判定・最少判定は、すべてこのユニット数で行う。** |
| **有効閾値** | `floor(総ユニット数 × 0.065)`（小数点以下切り捨て）。<br>グループのユニット数が **有効閾値以上** なら有効、**未満** なら統合対象。<br>例: 総ユニット数 387 → floor(387 × 0.065) = floor(25.155) = **25**。25 以上は有効、24 以下は統合。 |
| **アクティブ** | ユニットが 1 件以上入っている状態のグループを指す。 |
| **図鑑番号数** | あるグループに含まれるユニットの、図鑑番号（dex）の種類数。同じポケモンが複数リーグにまたがっても、図鑑番号が同じなら 1 と数える。<br>**丸め（8章）の大きさ基準としては使わない**（ユニット数に統一）。検索式の図鑑番号列（IV式のdex部分）の生成にのみ用いる。 |
| **段** | あるパターンが、**最も厳しいパターン**（こうげき01 / ぼうぎょ34 / HP34）から、その軸を何段緩めたかを表す整数。<br>・こうげき段 = a − 1（0〜2）<br>・ぼうぎょ段 = 3 − d（0〜2）<br>・HP段 = 3 − h（0〜2）<br>**丸めロジック（8章）での軸の比較・緩め判定は、すべてこの「段」で行う。** |
| **重み** | **パターンの並び順（PID順）を決めるためだけに使う値。** 定義は 7.3 に示す。<br>丸めロジックの手順には「重み」を使わない（丸めは「段」で判断する）。 |
| **緩める** | パターンの条件を広げる操作。次の 3 種類がある。<br>・こうげきを 1 段緩める: `a → a+1`（バケット上限を 1 上げる）<br>・ぼうぎょを 1 段緩める: `d → d−1`（バケット下限を 1 下げる）<br>・HPを 1 段緩める: `h → h−1`（バケット下限を 1 下げる） |
| **1手（いって）** | 丸めにおいて、くっつけ元パターンを規定の手順（8.3）で 1 回だけ緩め、別のパターンを求める操作。 |
| **くっつけ元** | 丸めで統合される側のグループ（およびそのパターン）。 |
| **くっつけ先** | 丸めで統合先となるパターン（およびそのグループ）。 |
| **個別枠** | どのグループにも属さないユニットの受け皿。1 枠のみ。 |
| **対象外領域** | パターンとして存在させない範囲。次の 3 つ。<br>・こうげき4（こうげき01234 = こうげき無制約）<br>・ぼうぎょ0（ぼうぎょ下限 0）<br>・HP0（HP下限 0）。 |

### パターンの詰め表記

パターンを一覧で示すときは、可読性のため次の詰め表記を用いる。
本文中の説明では正式名（こうげき/ぼうぎょ/HP）を用いる。

- 例: `こうげき01 / ぼうぎょ234 / HP234`
  = こうげきバケット `{0,1}`、ぼうぎょバケット `{2,3,4}`、HPバケット `{2,3,4}`。

## 3. 入力ファイル（iv_list_input.txt）

**入力フォーマット・受け入れ条件は本改訂で変更しない。O/M/L展開ルール（分岐の扱い）のみ本改訂で明確化した（下記）。**

### フォーマット

```
# ポケモン名/リーグ/TopN/対象指定
フシギダネ/S,H/200/L
ピカチュウ/S/300/L
リオル/S,H/1000/L
ベロリンガ/S/200/O
サイホーン/S/200/M
```

### 各項目の説明

| 項目 | 内容 |
|---|---|
| ポケモン名 | 日本語ポケモン名（pokedex_numbers.txtに収録されている名前） |
| リーグ | S（スーパー1500）/ H（ハイパー2500）/ M（マスター）、複数可（S,H） |
| TopN | SCPランキング上位何件を対象とするか（1〜4096） |
| 対象指定 | O=本人 / M=中間進化 / L=最終進化、複数可（L,M）。省略時は L。 |

### 対象指定（O/M/L）の展開ルール

> **O/M/L 展開ルールの正は `library.md`（3章 `expand_targets`）とする。本仕様書では展開ルールを定義しない。** 本アプリは library の `expand_targets` を用いて O/M/L を対象ポケモン種名へ展開する（`slim_cache_builder` と同一の部品を用いることで、キャッシュ生成種とアプリ参照種の食い違いを防ぐ）。

ルールの要点（詳細と判断表・検証済み例は `library.md`）:

- `O`＝入力したポケモン本人／`L`＝最終進化の段／`M`＝3段以上なら2番目の段、2段なら最終進化の段（＝L と同じ）。
- 指定した段に分岐（スラッシュ）があるときは、その段の分岐先をすべて対象にする。
- 進化しないポケモン（`evolution_map.txt` に未収録）は本人のみを対象にする。
- 段の数え方はカンマ＝段、スラッシュ＝同一段の分岐（`evolution_map_spec.md`）。進化マップは段構造を保持して読み込む（esal の `load_evolution_map_staged`）。

### 受け入れ条件（入力）

- ポケモン名が pokedex に未収録の行はエラーとして行番号付きで列挙し、処理を中断する。
- リーグ・対象指定に不正な記号が混じる行、TopN が整数でない／1〜4096 の範囲外の行も、同様にエラーとして列挙する。
- リーグ・対象指定の重複（例: `S,S`）は除去して扱う。
- コメント行（`#` で始まる行）と空行は読み飛ばす。
- 有効な行が 1 つも無い場合は警告を出して処理を止める。

## 6. ファミリーのIV決定ロジック

**本改訂で変更しない。** グループ分け（7章以降）より前の処理であり、各ユニットが「どのバケット集合を要求するか」をここで確定させる。

各ユニット（ポケモン×リーグ）について、slim_cache.json から TopN 件のランキングデータを取り出す。取り出す件数は「要求TopN・キャッシュが保持する件数・実際のエントリ数」の最小値とする。取り出した各エントリは `rank,atk_bucket,def_bucket,hp_bucket,atk_real` として解釈する。

このデータから、こうげき・ぼうぎょ・HPそれぞれについて採用するバケット集合を決定する。判定は次の複数ルールの和（いずれかで採用されたバケットを採る）とする。

### 全体10%ルール
TopN件全体で出現率10%以上のバケットを採用する。

### 上位30%10%ルール
TopN件の上位30%の中で出現率10%以上のバケットを採用する。

### SCP70拡張＋攻撃実数値強化
SCP上位70位以内の個体の中で、攻撃実数値トップ20件が持つこうげきバケットを強制採用する。

### フォールバック
上記いずれでも採用なしの場合、出現したバケットを全採用する。

### 決定後の扱い

- 同一ファミリー（＝同一の図鑑番号集合）に属する複数ユニットの要求バケットは、軸ごとに和を取ってまとめる。
- **ぼうぎょ または HP の要求バケットが空になったユニットは、以降の処理対象から除外する**（こうげきは除外条件に含めない）。
- ユニットの図鑑番号リストは、そのファミリー全員の図鑑番号を重複除去し昇順に並べたものとする。これを同一ファミリー判定のキーとする。

> 本ロジックの各ルールのパラメータ（10%・上位30%・70位・トップ20）は恒久的な前提であり、本改訂では触れない。

## 7. パターン集合（27通り）

本章と8章は、変更前仕様（23パターン＋ユニット数閾値でのグループ化）を**完全に置き換える**。変更前の「グループ1〜21は15以上／22〜23は5以上」といった閾値方式は廃止する。

### 7.1 対象範囲

| 軸 | 取りうる値 | 対象外 |
|---|---|---|
| こうげき上限 a | 1, 2, 3 | **a=4（こうげき01234）は対象外**（こうげきが高い個体は GBL で弱く、狙わない） |
| ぼうぎょ下限 d | 1, 2, 3 | d=0（ぼうぎょ0）は対象外 |
| HP下限 h | 1, 2, 3 | h=0（HP0）は対象外 |

→ 3 × 3 × 3 = **27通り**。実データ上の該当が 0 のパターンも、定義としてはすべて残す。

### 7.2 設計思想（なぜこの形か）

- 目的: ポケモンGO の GBL で強い個体を探すための検索キーワード生成。
- こうげきが高い個体は弱いため、こうげきは低く保つ（上限で刻む）。緩めるのは最後。
- ぼうぎょが高いほうが強い個体が多い（HP より ぼうぎょ を重視）。
  → 緩めるときは **HP を ぼうぎょ より先に** 緩める。
- ぼうぎょ と HP は、片方だけ極端に緩めず、バランスよく緩める。

### 7.3 重みの定義（並び順専用）

**重み = こうげき段 × 2 + ぼうぎょ段 × 1 + HP段 × 1**

- こうげき 1 段の重みは **2**（HP・ぼうぎょ の 1 段は重み 1）。
- こうげきを緩めることを重く扱い、こうげきを緩めたパターンを後ろへ回す。
- **この「重み」は 7.4 の並び順を決めるためだけに使う。** 丸めロジック（8章）では使わない。

### 7.4 並び順（PID順）ルール

割り当て（8.2）は PID の若い順にパターンを走査し、ユニットが収まる最初のパターンに入れる
（若い = 優先 = 厳しい）。並び順は次のキーで決定する（上から優先）。

1. **重み** が小さい順。
2. **ぼうぎょ段 と HP段 のバランス**: `|ぼうぎょ段 − HP段|` が小さい順（片方だけ極端に緩めない）。
3. **HP優先**: HP段 が大きいほうを先（HP を先に緩めたパターンを優先）。
4. **こうげき**: こうげき段 が小さいほうを先（こうげきは最後まで絞る）。

## 8. グループ丸め（統合）ロジック

### 8.1 大きさの基準

グループの大きさは、すべて **ユニット数**（そのグループに割り当てられたユニットの件数）で測る。
以降の「有効閾値未満」「いちばん小さい」等の判定は、すべてユニット数で行う。
（rev1.1 までは図鑑番号数で測っていたが、rev1.2 でユニット数に統一した。）

### 8.2 割り当て（閾値なし）

- 27 パターンに PID の若い順で走査し、ユニットが収まる最初のパターンに入れる。
  - 「収まる」= ユニットの各軸バケット集合が、そのパターンの各軸バケット集合に含まれること。
- **割り当て段階の最小ユニット数の閾値は設けない**（変更前の閾値方式を廃止）。小さいグループは 8.5 の丸めで統合される。
- どのパターンにも収まらなかったユニット（こうげきバケット4=IV15 を含む個体、ぼうぎょ0・HP0 を含む個体など27パターンの対象外）は、個別枠へ入れる。

### 8.3 1手（くっつけ先の求め方）

くっつけ元パターン `(a, d, h)` を起点に、次の手順で **くっつけ先パターンを 1 つ** 求める。
判定はすべて「段」で行う（こうげき段・ぼうぎょ段・HP段）。

- **第1段階**: HP段 と ぼうぎょ段 が **異なる** なら、**段が小さい軸を 1 段緩める**。
  - ぼうぎょ段 < HP段 → ぼうぎょを 1 段緩める（d を 1 下げる）。d が既に 1 なら緩め先はぼうぎょ0＝**対象外**。
  - HP段 < ぼうぎょ段 → HP を 1 段緩める（h を 1 下げる）。h が既に 1 なら緩め先はHP0＝**対象外**。
- **第2段階**: HP段 と ぼうぎょ段 が **等しい** ときのみ。次の優先順で、最初に可能なものを選ぶ。
  1. **HP を 1 段緩める**（h を 1 下げる）。
  2. 上が不可なら **ぼうぎょを 1 段緩める**（d を 1 下げる）。
  3. 上も不可（＝ h も d も既に下限 1）なら **こうげきを 1 段緩める**（a を 1 上げる）。
  4. こうげきも既に上限（a=3）なら、緩め先はこうげき4＝**対象外**。

「対象外」を返した場合、そのくっつけ元グループのユニットは **個別枠へ落とす**（8.4 / 8.5 参照）。

> **補足（なぜ第2段階は3択で足りるか）**: 緩めはバケットを1個ずつ広げる操作なので、「1段緩められない」＝「その軸はもう限界まで広がっている」を意味する。したがって「1段は無理だが2段なら可能」という状況は原理的に存在せず、2段緩めや両軸同時緩めは決して選ばれない。上から順に見て最初に可能なもので即決するため、実際に起こるのは「HPを緩める／ぼうぎょを緩める／こうげきを緩める／対象外」のいずれかに限られる。

#### 検証済みの例（受け入れ条件）

実装は、次の入力に対して次のくっつけ先を返すこと。

| くっつけ元 | 判定 | くっつけ先 |
|---|---|---|
| こうげき01 / ぼうぎょ34 / HP34 | HP段=ぼうぎょ段（ともに0）→ 第2段階 HP を緩める | こうげき01 / ぼうぎょ34 / HP234 |
| こうげき01 / ぼうぎょ34 / HP234 | HP段1 > ぼうぎょ段0 → 第1段階 ぼうぎょを緩める | こうげき01 / ぼうぎょ234 / HP234 |
| こうげき01 / ぼうぎょ234 / HP234 | HP段=ぼうぎょ段（ともに1）→ 第2段階 HP を緩める | こうげき01 / ぼうぎょ234 / HP1234 |
| こうげき01 / ぼうぎょ1234 / HP1234 | HP段=ぼうぎょ段（ともに2, 最大）→ 第2段階 こうげきを緩める | こうげき012 / ぼうぎょ1234 / HP1234 |
| こうげき0123 / ぼうぎょ1234 / HP1234 | 全軸最大、こうげきも上限 → 対象外（こうげき4）→ 個別枠 | （なし・個別枠へ） |

### 8.4 くっつけ先の扱い（空パターン・端）

- **空パターンでも、くっつけ先にできる。**
  8.3 が返したパターンに、その時点でユニットがいなくても（＝空でも）、そこへ移す。
  結果として空だったパターンが新しいグループになる。
  丸めルール上「条件が最も近いパターン」にまとまるため、元の条件に近い形を保てる。
  「もともと空だったグループが有効閾値以上に育つ」ことは起こり得るが、望ましい挙動として許容する。
- **8.3 が「対象外」を返したら、そのくっつけ元グループは個別枠へ落とす。**
  対象外領域（こうげき4・ぼうぎょ0・HP0）に到達した = これ以上緩める先がない（緩い端）とみなす。

### 8.5 全体フロー（割り当て → 丸め込み巡回方式）

処理は次の 2 ステップを順に行う。

**割り当て（閾値なし）**
各ユニットについて、PID 昇順にパターンを走査し、収まる最初のパターンへ割り当てる（8.2）。
どのパターンにも収まらないユニットは個別枠へ入れる。

**丸め込み（巡回＝ラウンド方式）**
はじめに有効閾値を 1 回だけ算出し、以降固定する。

- `有効閾値 = floor(総ユニット数 × 0.065)`
  - 総ユニット数は全ユニット（FamilyUnit）数。個別枠のユニットも含む。丸め込み中は再計算しない。

**1 巡（ラウンド）** を、閾値未満のグループが無くなるまで繰り返す。1 巡は次の手順で行う。

- 巡の開始時点で、アクティブなグループのうち **ユニット数が有効閾値未満** のものを**すべて集める**（これをこの巡の「処理対象リスト」とする。巡の途中でリストは作り直さない）。
- 処理対象リストが空なら、全体を終了する。
- 処理対象リストのグループを **ユニット数が少ない順**（同数なら PID が小さい＝より厳しいグループを優先）に、**1 つずつ、この巡で 1 回だけ**緩める：
  - 8.3 の 1手 でくっつけ先を求め、対象外なら個別枠へ、そうでなければくっつけ先グループ（空でも可）へ移す。
  - **その巡で合流先（くっつけ先）になったグループは、その巡ではもう緩めない。** これは合流先が「この巡の処理対象リストに元々入っていたかどうか」に関わらず適用する。処理対象リストに入っていたグループでも、他グループの合流先になった時点で、その巡の残りでは緩めない（保護する）。
  - 言い換えると、**1 巡の中で同じグループが 2 回以上緩むことはない**（緩め元として 1 回緩むか、合流先として保護されて 0 回か、のいずれか）。移送でユニット数が増減しても、その巡では動かさない。合流先を含め、閾値未満かどうかを評価し直すのは次の巡の開始時点。
- 巡内の全対象を処理し終えたら、その巡を終える。次の巡の開始時に、あらためて閾値未満のグループを集め直す。

この「1 巡 = 各対象を 1 回ずつ」という区切りが重要である。複数の小グループが同じ合流先に集まって閾値以上へ育つ機会を、合流先が続けて緩められる前に与える。これにより、合流先が閾値に届く前に過剰に緩められる現象（例: こうげきを緩めずに済むはずのグループが、連続緩めでこうげきまで広がる）を防ぐ。

#### 巡回方式の検証済みの例（受け入れ条件）

有効閾値 25、次の 2 グループがともに閾値未満だとする（他は省略）。

- G_A = こうげき01 / ぼうぎょ234 / HP1234（22 ユニット）
- G_B = こうげき01 / ぼうぎょ1234 / HP234（23 ユニット）

1 巡目：処理対象リスト = {G_A, G_B}（巡の開始時点で固定）。

- G_A を 1手 緩める → 8.3 によりぼうぎょを緩め、`こうげき01 / ぼうぎょ1234 / HP1234`（= P）へ移す。P は合流先になった。
- 続いて G_B を 1手 緩める → 8.3 により HP を緩め、同じ P へ移す。P に 22+23=45 が集まる。
- P はこの巡で合流先になったグループなので、**この巡ではもう緩めない**（保護）。

2 巡目：あらためて閾値未満を集めると、P は 45（≥25）なので対象外。他に閾値未満が無ければ終了。

- 結果：P = `こうげき01 / ぼうぎょ1234 / HP1234` のまま残り、**こうげきは緩まない**。
- 逐次方式（Rev1.2）では、G_A を P に移した直後に P（22）が最少として再選択され、G_B が来る前に P がこうげきまで緩められてしまっていた。巡回方式はこれを防ぐ。

**グループ数の上限は設けない。** 「有効閾値以上」という条件から、グループ数は自然に絞られる
（各グループが総数の 6.5% 以上なら、最大でも約 15 グループ）。

補足:

- 大きさ・閾値・最少判定は、すべてユニット数（8.1）。図鑑番号数は使わない。
- 有効閾値は「以上=有効 / 未満=統合対象」。例: 閾値25 なら 25 以上は残す、24 以下は統合。
- くっつけ先は 8.4 の通り、空パターンでも可。対象外領域に到達したら個別枠へ。
- 統合により受け皿グループのユニット数が大きくなっても、**分割はしない**（許容する）。
- 処理は必ず停止する: 各巡で、その巡の処理対象（開始時点で閾値未満だったグループ）は必ず 1 回ずつ緩められ（合流または個別枠化）、その場所からは消える。緩めは軸を広げる操作で有限回で対象外（端）に達するため、巡を重ねれば閾値未満グループは無くなるか個別枠へ移る。
- 総ユニット数が小さく `有効閾値 = 0` になる入力では、「未満」が発生しないため最初の巡で即終了する（全グループ有効）。これは正しい挙動で、特別扱いは不要。

### 8.6 受け入れ条件（丸め）

- 8.5 の処理を終えた時点で、**個別枠を除くアクティブなグループは、すべてユニット数が有効閾値以上**であること。これが本改訂の実装が満たすべき最終状態の基準である。
  - グループ数に上限は無い（6 以下に収束させる必要は無い）。
  - どのPIDに何ユニット入るか、といった個々の数値は基準としない（入力データに依存するため）。
- 個別枠は有効閾値の判定対象外（ユニット数が閾値未満でもよい）。
- 総ユニット数（ヘッダーの「ユニット数：N」）は、丸め込み前後で変化しないこと（全グループのユニット数合計＋個別枠のユニット数＝総ユニット数）。
- 空パターンがくっつけ先になり得ること（8.4）。
- 対象外領域に到達したくっつけ元は個別枠へ落ちること（8.3 表5行目、8.4）。
- 大きさ・最少・閾値の判定はすべてユニット数で行い、図鑑番号数では行わないこと。

## 9. 出力（iv_list_output.txt）

出力全体は、ヘッダ → 冒頭固定ブロック → グループブロック（アクティブグループごと）→ 個別枠ブロック → 末尾固定ブロック の順に並ぶ。行はすべて `\n` で連結する。

### 9.1 固定文字列（フィルタ）

検索式の末尾に付くフィルタは次のとおり。

| 用途 | フィルタ文字列 |
|---|---|
| GBL用・レイド用の除外 | `&!お気に入り&!#&!しゃどう&!だいまっくす&!きょだいまっくす` |
| 確認用の付与 | `&お気に入り,#&!しゃどう&!だいまっくす&!きょだいまっくす` |
| トレードタグ除外 | `&!#交換&!#内交換&!#リモート交換&!#100km&!#300km` |
| 博士送り用の除外 | `&!お気に入り&!#&!しゃどう&!色違い&!だいまっくす&!きょだいまっくす` |

### 9.2 ヘッダ

先頭行に次の1行を出力し、続けて空行を1行置く。

```
# {日時} ユニット数：{総ユニット数}  ポケモンGO 検索キーワード
```

- `{日時}` は日本時間（UTC+9）で `YYYY/MM/DD HH:MM` 形式。
- `{総ユニット数}` は処理対象となった全ユニット数。
- 「ユニット数：」の直後の全角コロンの後、および「ポケモンGO」の前は、変更前の表記を維持する（`ユニット数：{数}␣␣ポケモンGO`。半角スペース2つ）。

### 9.3 冒頭固定ブロック

ヘッダの後に、次を出力する。100%個体の後は空行1行、0%個体の後は空行2行（ブロック区切り）。

```
# 100%個体
4*

# 0%個体
0こうげき&0ぼうぎょ&0HP
```

### 9.4 グループブロック（アクティブグループごと）

アクティブなグループを PID 昇順に出力する。各グループは次の5項目からなる。項目間は空行1行、グループ末尾（博士送り用）の後は空行2行（グループ区切り）とする。

プレースホルダの意味:

- `{PID}`：パターンID。**ゼロ埋め2桁**（例: PID4 → `G04`）。
- `{N}`：位置（スロット番号）。**アクティブグループと個別枠を、出力順に 1 から数えた通し番号**（PIDとは別。空グループは数えない）。
- `{T}`：総スロット数。**アクティブグループ数 ＋ 個別枠の有無（個別枠があれば +1、なければ +0）**。
- `{U}`：そのグループの**ユニット数**（図鑑番号数ではなく、割り当てられたユニットの件数）。
- `{IV式}`：そのグループのパターンのバケット式（9.6 の規則で生成）。
- `{図鑑番号}`：そのグループの全ユニットの図鑑番号を、重複除去・昇順・カンマ区切りにした文字列。

```
# G{PID}-GBL用(位置：{N}/{T} ユニット数：{U} IV：{IV式})：SCP重視の検索
{図鑑番号}&{IV式}&!お気に入り&!#&!しゃどう&!だいまっくす&!きょだいまっくす

{図鑑番号}&3こうげき,4こうげき&3ぼうぎょ,4ぼうぎょ&3HP,4HP&!お気に入り&!#&!しゃどう&!だいまっくす&!きょだいまっくす

{図鑑番号}&お気に入り,#&!しゃどう&!だいまっくす&!きょだいまっくす&!#交換&!#内交換&!#リモート交換&!#100km&!#300km

# G{PID}-最終確認用(位置：{N}/{T} ユニット数：{U})：すべてのポケモン検索
{図鑑番号}&!#交換&!#内交換&!#リモート交換&!#100km&!#300km

# G{PID}-博士送り用(位置：{N}/{T} ユニット数：{U})：お気に入り、タグ付けをしなかったポケモン検索
{図鑑番号}&!お気に入り&!#&!しゃどう&!色違い&!だいまっくす&!きょだいまっくす
```

- **レイド用の検索式は、グループのパターンに関わらず常に上記の固定式**（`3,4こうげき&3,4ぼうぎょ&3,4HP`）とする。
- 確認用・最終確認用は 9.7 の出力制御に従う（デフォルトOFF）。

### 9.5 個別枠ブロック

グループブロックの後に、個別枠を出力する。個別枠は「どのグループにも属さないユニット（＝どのパターンにも収まらなかったユニット、および丸めで対象外に落ちたユニット）」の受け皿である。

`{図鑑番号}` は個別枠の全ユニットの図鑑番号を重複除去・昇順・カンマ区切りにしたもの。`{N}`・`{T}`・`{U}` はグループと同じ規則（個別枠は最後のスロット）。

**個別枠に該当ユニットがある場合**（項目間は空行1行、博士送り用の後は空行1行）:

- 個別枠でも、GBL用・レイド用の検索式には IV式（こうげき/ぼうぎょ/HP）を付けない。図鑑番号とフィルタのみ（レイド用は固定式）とする。

```

```

### 9.6 IV式の生成規則

`{IV式}` は、そのグループのパターンから次のように作る。

- こうげき・ぼうぎょ・HP の順に、各軸のバケット集合を文字列化して `&` で連結する。
- 各軸内は、バケット番号を昇順に並べ、`{番号}{軸名}` の形（軸名は `こうげき`・`ぼうぎょ`・`HP`）を `,` で区切る。
  - 例: こうげきバケット `{0,1}` → `0こうげき,1こうげき`。
  - 例: ぼうぎょバケット `{2,3,4}` → `2ぼうぎょ,3ぼうぎょ,4ぼうぎょ`。
- 3軸を連結した例: `0こうげき,1こうげき&2ぼうぎょ,3ぼうぎょ,4ぼうぎょ&2HP,3HP,4HP`。
- **7章の対象範囲により、こうげき・ぼうぎょ・HP のいずれも無制約（0〜4すべて）にはならない。したがってグループ枠のGBL用検索式・IV式では、常に3軸すべてを出力する**（無制約による軸の省略は行わない）。

### 9.7 確認用・最終確認用の出力制御

- **GBL用・レイド用・博士送り用は常に出力する。**
- **確認用・最終確認用はデフォルト OFF**。画面のチェックボックスで ON にしたときのみ出力する。
- この制御は **グループ枠・個別枠の両方に適用する**。OFF の項目は、そのコメント行・検索式・直後の空行ごと出力しない。

### 9.8 末尾固定ブロック

個別枠ブロックの後に空行1行を置いてから、次を出力する。項目間は空行1行、最後の「色違い」の後には空行を置かない。

```
# 最後の確認用
!お気に入り&!#&!しゃどう&!色違い&!だいまっくす&!きょだいまっくす

# 伝説,幻,ウルトラビースト
伝説のポケモン,まぼろし,ウルトラビースト&!お気に入り&!#

# ダイマックス、キョダイマックス
だいまっくす,きょだいまっくす&!お気に入り&!#

# 色違い
色違い&!お気に入り&!#
```

### 9.9 空行規則（まとめ）

空行は2段階の階層で入れる。

- **項目間は空行1行**（コメント行＋検索式を1項目とし、その後に1行）。
- **ブロック間は空行2行**。具体的には、冒頭固定ブロック（0%個体）の後、各グループの末尾（博士送り用）の後。
- 個別枠ブロックの各項目間は空行1行、個別枠の末尾（博士送り用または「個別枠-該当なし」）の後は空行1行。
- 末尾固定ブロックに入る前に空行1行を置く。
- 末尾固定ブロックの項目間は空行1行、最後の「色違い」の後は空行なし。

### 9.10 受け入れ条件（出力）

- チェックボックスが両方 OFF のとき、確認用・最終確認用の行がグループ枠・個別枠のいずれにも出力されないこと。
- チェックボックスを ON にしたとき、対応する行が出力されること。
- GBL用・レイド用・博士送り用は、チェックボックスの状態にかかわらず常に出力されること。
- コメント行のコロンはすべて全角（`位置：`・`ユニット数：`・`IV：`・説明文前の `）：`）。
- 位置（`{N}/{T}`）は、アクティブグループと個別枠を出力順に1から数えた通し番号／総スロット数と一致すること。
- レイド用は常に固定式であること。IV式は常に3軸すべてを含むこと。
- 末尾固定ブロックは常に出力されること。
