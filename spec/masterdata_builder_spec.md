## 1. 概要

ポケモンを新規追加するとき、これまで手作業で編集していた `master_data/` の各ファイルへの追記を、UI 入力から定型的に生成・追記するローカルツール。

- **形態**: ローカル実行の Streamlit アプリ（手元のブラウザに UI が出る）。
- **配置**: リポジトリ直下 `masterdata_builder/app.py`（既存アプリと同じ「フォルダ＋app.py」形式）。
- **起動**:
  ```bash
  cd C:\GitHub\Pokemon-go-tools
  streamlit run masterdata_builder/app.py
  ```
- **書き換え対象**: `master_data/` 配下の 3 ファイル（`pokedex_numbers.txt`・`evolution_map.txt`・`iv_list_input.txt`）。ローカルのファイルを直接追記する。旧ツール `data_checker.py` やその設定ファイル `tools/data_checker_support.txt` には一切関与しない。

### 目的

最終成果物（`master_data/` の各ファイル）に不整合が無い状態を保ちながら、新規ポケモンの追加を省力化する。手作業での複数ファイル編集をなくす。

### 基本原則（重要）

- **ツールは値や名前を考えない。** 図鑑番号・種族値・名前・進化構造・検索設定は、すべてユーザーが入力する。ツールは入力に沿って、決められた書式へ整形して追記するだけ。
- **新規追加のみ。** 既存データの編集・削除は行わない。
- **既存ファイルがある前提。** ゼロからファイルを生成しない。末尾へ追記する。

## 2. 層構造

既存の移行済みアプリ（id_generator・iv_strings_generator）と同じ 4 層構造に従う。

| 層 | 場所 | 責務 |
|---|---|---|
| UI | `masterdata_builder/app.py` | Streamlit の画面・入力欄・確認画面・ボタン。ロジックは呼ぶだけの薄い層。 |
| features | `src/masterdata_builder/` | このツール固有の純粋ロジック（入力→追記行への整形、単体/系統の判定、重複照合の判定など）。 |
| library | `src/library/` | 複数アプリ共通の純粋処理。本ツールは `expand_targets` を確認画面の展開に使う（`library.md`）。 |
| esal | `src/esal/` | 外部ファイルとの読み書き境界。読み込み（既存の `load_evolution_map_staged`・`load_pokedex` 等）に加え、**本ツールで追記（書き込み）関数を新設**する。 |
| test | `tests/masterdata_builder/` | features 層のテスト。 |

- 依存の向きは `features → library / esal` を守る（逆向きを作らない）。
- **esal の役割を「読み込み専用」から「外部ファイルとの読み書き両方の境界層」へ拡張する。** ファイル I/O を esal 1 層に集約する（読みは features、書きは別、と散らさない）。

## 3. 入力（ユーザーが与えるもの）

ツールは以下をユーザーから受け取る。ツールはこれらの値を生成・補完・推測しない。

### 3.1 系統の各メンバー

進化系統に登場する**全メンバー**（起点・進化先・分岐先すべて）について、1 匹ずつ以下を入力する。`pokedex_numbers.txt` に載る全員が対象。

- 名前
- 図鑑番号（実在の値。別フォルム同番号などは実在の番号どおりに入力する）
- 種族値：HP・攻撃・防御

**入力欄の並び（表示のみ）**：UI 上は横一列に `名前・図鑑番号・攻撃・防御・HP` の順で入力欄を並べる。これは入力のしやすさのための表示順であり、**内部データおよび `pokedex_numbers.txt` への書き込み順は従来どおり `名前・図鑑番号・HP・攻撃・防御`**（4.1）を維持する。表示順と書き込み順は独立している。

**行の増減**：メンバーは「追加」「最後を削除」で 1 匹ずつ増減できる（イーブイ系など多分岐の系統に対応するため）。

### 3.2 進化系統の構造

「段ごとに欄を足す」方式で入力する（`evolution_map.txt` の構造と 1 対 1 対応）。

- 段を追加でき、各段に 1 つ以上のメンバー名を置ける。段は「追加」「最後を削除」で増減できる。各段のメンバーは 3.1 で入力済みのメンバー名から選ぶ。
- 同一段に複数メンバーを置くと分岐（`/`）を表す。
- カンマ＝段、スラッシュ＝同一段の分岐（形式の正は `evolution_map_spec.md`）。

**表示（表示のみの変更）**：

- セクション名は「進化先設定」とする。
- 段ラベルは段の位置と総段数から動的に決める：最初の段＝「進化前」、最後の段＝「最終進化」、間の段＝「中間進化」。段を追加・削除するとラベルも切り替わる。
  - 例（2 段：オラチフ→マフィティフ）：進化前 / 最終進化。
  - 例（3 段：フシギダネ→フシギソウ→フシギバナ）：進化前 / 中間進化 / 最終進化。

#### 単体（進化しない）か系統かの自動判定

- 段が 1 つ（起点のみ、進化先なし）→ **単体**とみなす。
- 段が 2 つ以上 → **系統**とみなす。
- ユーザーはこの区別を明示的に選ばない。段の入力結果から自動で判定する。

### 3.3 検索設定（複数行）

検索設定は**行を複数追加できる**。既存 `iv_list_input.txt` と同じ書式で、対象ごとに TopN・リーグ・対象指定を独立して指定できる（対象ごとに TopN を変えられる）。

各行は横一列で以下を指定する（UI 上は `対象ポケモン・リーグ・TopN・対象指定` の順に並べる）。

- **対象ポケモン**：メンバー登録で入力した**全メンバーから選ぶ**（起点だけでなく進化先・分岐先も選択肢に出す）。選んだポケモンが、生成される行の名前欄に入る。
- **リーグ**：S・H から選択（複数可）。
- **TopN**：検索希望順位。1〜4096。
- **対象指定（O/M/L）**：複数可。展開ルールの正は `library.md`。
  - `O`＝選んだポケモン本人。`M`＝中間進化。`L`＝最終進化。
  - **ラベル表示（表示のみ）**：UI 上の対象指定ラベルは「対象指定（O/M/L）」と短く表示し、`O`・`M`・`L` の意味説明（O＝自身／M＝中間進化／L＝最終進化）は入力欄の help（ツールチップ）に置く。長いラベルによる列のレイアウトずれを避けるため。書き込む値は従来どおり `O`・`M`・`L`。

行の追加・削除ができる（「行を追加」「最後の行を削除」）。単体（進化しない）の場合、対象ポケモンは本人のみで、対象指定は O のみが有効（3.3.1 の検証に従う）。

#### 3.3.1 対象指定の妥当性（無効な組み合わせの検証）

選んだ対象ポケモンが系統のどの段にいるかで、有効な O/M/L が変わる。無効な組み合わせが指定された場合、**生成ボタン押下時に理由付きエラーで弾き、書き込ませない**（入力画面に留まる）。選択肢を消すのではなく、理由を提示する方針とする。

- 起点（最初の段）を選んだ場合：O・M・L いずれも有効（M・L はその系統の中間段・最終段を指す）。
- 最終進化（最後の段）を選んだ場合：**O のみ有効**。M・L はその先の進化が無いため無効。
- 中間段のポケモンを選んだ場合：本人（O）が有効。M・L は「その段から見た先の段」を指すため、実際に展開先が存在するかで判定する。
- 単体（進化なし）：O のみ有効。

無効時のエラーは、理由と対処を添える（例：「マフィティフは最終進化のため、指定できるのは O のみです。中間・最終進化を対象にしたい場合は、起点のオラチフを選んで M・L を指定してください」）。

> 判定は、対象ポケモンを `expand_targets` に渡した展開結果に、**対象ポケモンより後の段（＝進化先）のポケモンが 1 つでも含まれるか**で行う。含まれれば有効、含まれなければ無効とする。単に「展開結果が空か」で判定すると、最終段に `L` を指定したとき本人が返って空にならず、誤って有効と判定しうるため、「対象より後の段が含まれるか」で判定する。展開ロジックの正は `library.md`。本書は有効/無効の考え方を定め、判定の実装（後段メンバー集合との照合など）は委ねる。

## 4. 生成・追記の対象と書式

判定結果（系統／単体）によって、追記するファイルが変わる。ツールは値を考えず、入力を下記の書式へ整形して各ファイル末尾へ追記する。

### 4.1 系統ありの場合

| ファイル | 追記内容 |
|---|---|
| `pokedex_numbers.txt` | 系統の**全メンバー**について 1 行ずつ。書式は既存に従い、タブ区切り `名前<TAB>図鑑番号<TAB>HP<TAB>攻撃<TAB>防御`。 |
| `evolution_map.txt` | 系統を 1 行。カンマで段区切り、スラッシュで同一段の分岐（3.2 の入力構造をそのまま文字列化）。 |
| `iv_list_input.txt` | 検索設定を追記（4.3 の書式に従う）。 |

### 4.2 単体（進化しない）の場合

| ファイル | 追記内容 |
|---|---|
| `pokedex_numbers.txt` | 本人 1 行（書式は 4.1 と同じ）。 |
| `iv_list_input.txt` | 本人の検索設定を追記。対象指定は **O 固定**（4.3 の書式に従う）。 |

- 単体は `evolution_map.txt` には**書かない**（進化系統が無いため）。
- 単体でも系統でも、本ツールが書き込むのは `master_data/` の上記ファイルのみ。`tools/data_checker_support.txt` には書き込まない（8 章参照）。

### 4.3 iv_list_input.txt の追記書式（1 検索行＝1 出力行）

検索設定の**各行**（3.3）は、そのまま `iv_list_input.txt` の**1 行**に対応させる。ツールは行を分割・統合しない。ユーザーが検索設定で作った行数のまま、その行で選んだ複数リーグ・複数対象指定を、それぞれカンマで連結して 1 行にまとめる。

- 書式は既存に従い `対象ポケモン名/リーグ/TopN/指定`。名前欄には、検索設定の行で選んだ対象ポケモン名が入る。
- リーグを複数選んだ場合はカンマで連結（例：`S,H`）。対象指定を複数選んだ場合もカンマで連結（例：`L,M`）。
- **検索設定の行数＝追記される行数**（1 対 1）。行を分けるかまとめるかはユーザーの入力（検索行の分け方）に従い、ツールは判断しない。
  - 例（マフィティフを S・H／200／O で 1 行指定）:
    ```
    マフィティフ/S,H/200/O
    ```
  - 例（マンキーを S・H／200／L・M で 1 行指定）:
    ```
    マンキー/S,H/200/L,M
    ```
  - 例（対象ごとに TopN を変えたいので 2 行に分けて指定：オラチフ S/500/O と マフィティフ S/100/O）:
    ```
    オラチフ/S/500/O
    マフィティフ/S/100/O
    ```
  - 例（単体・ガルーラを S で検索、O 固定）:
    ```
    ガルーラ/S/1000/O
    ```

> 本ツールが追記する行は、既存 `iv_list_input.txt` の手入力行と同じ書式（リーグ・対象指定をカンマでまとめた形）になる。既存行を書き換えることはしない（追記のみ）。

## 5. 処理フロー（確認フロー）

ユーザーの入力が期待どおりかを、書き込み前に確認させる。

1. **入力画面**：3 章の情報を入力する。
2. **「生成」ボタン**を押す。
3. **入力バリデーション**：生成時に以下をまとめて検証し、1 つでも問題があれば理由を表示して**入力画面に留まる**（書き込まない・入力は保持）。
   - 段（進化先設定）が 1 つ以上あるか。
   - メンバー名が入力されているか。段に選ばれたのに種族値が未登録のメンバーがいないか。
   - 検索設定が 1 行以上あるか。各行に対象ポケモン・リーグ・対象指定が選ばれているか。
   - 各検索行の対象指定（O/M/L）が妥当か（3.3.1）。
4. **既存データとの照合**（7 章）：ファイルごとに既存と照合する。**全体を止めることはしない**（照合結果は確認画面で伝える）。既存は一切変更しない。
5. **確認画面**：ユーザーの入力が期待どおりかを**意図目線**で表示し、あわせて照合結果（新規追加／既存と一致／既存と不一致の差分／iv_list の重複スキップ）を伝える（6 章）。
6. **ユーザーの選択**：
   - **OK** → 各ファイルへ追記する（4 章）。追加されるのは「既存に無いもの」だけ（7 章でスキップ・非追加と判定したものは書き込まない）。
   - **修正** → 入力画面へ戻る。**前回入力は消さない**（Streamlit の session_state で保持）。
7. **完了表示**：追記が終わった旨を表示する。

## 6. 確認画面の表示内容

確認画面は「どのファイルに何行書くか」というファイル目線ではなく、**ユーザーの入力が意図どおりかを確認できること**を目的とする。表示は項目名付きの見やすい形（表など）とし、書き込む生テキストは主目的ではない。

表示する内容:

- 入力した系統の段構造（例：ラルトス → キルリア → サーナイト・エルレイド〈分岐〉）。
- 各メンバーの種族値（入力値の確認）。**メンバー一覧テーブルの表示順は「名前・図鑑番号・攻撃・防御・HP」**とする（入力欄の並びと揃える。表示のみで、`pokedex_numbers.txt` への書き込み順は 4.1 のとおり不変）。
- 検索設定の**各行**（対象ポケモン・リーグ・TopN・対象指定）を行ごとに表示する。
- **各行の指定での実際の検索対象**（分岐進化で最も間違えやすいため、行ごとに明確に見せる）。
  - 例：ケムッソに L → 検索対象は カラサリス・マユルド。
- **既存データとの照合結果**（7 章）。ユーザーが「何が追加され、何が追加されないか」を把握できるよう、ファイルごとに区別して伝える：
  - 新規に追加されるもの。
  - pokedex・evolution_map で「同じ内容で既に存在」するもの（追加しない）。
  - pokedex・evolution_map で「既に存在するが内容が違う」もの（追加しない・書き換えない。既存と入力の**差分**を表示し、手動チェックを促す）。
  - iv_list_input で対象（ポケモン×リーグ）が重複しスキップされるもの（「すでに対象のポケモンが存在するため追加しません」の趣旨＋重複した既存行を表示）。

### 6.1 検索対象の展開方法（重要）

確認画面に出す「実際の検索対象」は、**library の `expand_targets` を用いて展開する**。iv_list_input を実際に使う `slim_cache_builder` や `iv_strings_generator` と同一ロジックで見せることで、「確認画面ではこう出たが実際は違う」というずれを防ぐ。

- `expand_targets` には**段構造の進化マップ**を渡す必要がある。確認画面では、**既存 `evolution_map.txt` を読み込んだ段構造に、いままさに入力中の新系統を合成したもの**を渡す（新系統はまだファイルに書かれていないため）。
- 展開ルール（O＝本人／L＝最終段の全枝／M＝中間段〈3段のみ、2段は L と同義〉／未収録は本人）の正は `library.md`。本書では定義しない。

## 7. 既存データとの照合（ファイルごと・追加のみ）

**大前提：既存の `master_data`（3 ファイルすべて）は一切変更しない。本ツールは追加だけを行う。** 既存データに不整合や誤りがあっても、書き換え・修正・削除はしない（誤りに気づかせるのは人の手動チェックのため）。

3 ファイルは同期しておらず、一部のファイルにしか存在しないポケモンがある。そのため「名前がどこかにあれば全体を弾く」旧方式は使わない。**ファイルごとに独立して照合し、そのファイルにまだ無いものだけを追加する。全体は止めない。** 照合結果は確認画面（6 章）で伝える。読み込みは esal を用いる。

### 7.1 pokedex_numbers.txt の照合

追加しようとする各メンバー（名前）について、既存 `pokedex_numbers.txt` を照合する。

- **既存に無い** → 追加する。
- **既存にあり、内容が一致**（図鑑番号・HP・攻撃・防御がすべて入力と同じ）→ 追加しない。「同じ内容で既に存在します」と伝える（差分は出さない）。
- **既存にあり、内容が不一致** → 追加しない・**書き換えない**。「既に存在しますが内容が違います」として、**既存と入力の差分を表示**し、手動チェックを促す。

### 7.2 evolution_map.txt の照合

追加しようとする系統（段構造）について、既存 `evolution_map.txt` を照合する。名前を含む既存の系統行があるかで見る。

- **既存に無い** → 追加する。
- **既存にあり、段構造が一致** → 追加しない。「同じ内容で既に存在します」と伝える。
- **既存にあり、段構造が不一致** → 追加しない・**書き換えない**。既存の系統行と入力の系統を並べて**差分を表示**し、手動チェックを促す。
- （単体は evolution_map に書かないため、この照合の対象外。）

### 7.3 iv_list_input.txt の照合

iv_list_input は「同じポケモンを別表記で指す行」（例：`サイホーン/S/../L` と `ドサイドン/S/../O` はどちらもドサイドンの S）や、1 行での複数指定があり、表面的な文字列比較では同一対象かを判定できない。そこで **`expand_targets` で展開した「対象ポケモン × リーグ」の集合**で照合する。

- 追加しようとする各検索行を展開し、「対象ポケモン × リーグ」の集合を得る。
- 既存 `iv_list_input.txt` の**全行**も同様に展開して、既存の「対象ポケモン × リーグ」集合を得る（手入力由来の省略形行も expand_targets で展開できる）。
- 追加行の対象 × リーグが**既存に無い** → 追加する。
- **既存と重複する** → その行を**自動でスキップして追加しない**。重複した対象を iv_list_input に増やすと `iv_strings_generator` が期待どおり動かない恐れがあるため、ユーザーの操作どおりに追加せず、機械的に重複を防ぐ。
  - 確認画面で「すでに対象のポケモンが存在するため追加しません」の趣旨を明示し、**重複した既存行**も一緒に表示する（例：追加しようとした `サイホーン/S/500/L`〈対象：ドサイドン〉に対し、既存 `ドサイドン/S/1000/O`）。ユーザーが「操作どおりに追加されない」ことにはっきり気づけるようにする。文言は実装時に自然な表現へ調整してよい。

> 図鑑番号の重複（別フォルム等で正当に発生）は、ここでは扱わない。

## 8. 既存 data_checker.py との関係

- 本ツールは `data_checker.py` を呼び出さず、その設定ファイル `tools/data_checker_support.txt` にも一切書き込まない。**旧ツールを意識した実装は行わない。**
- 本ツールは「壊れたデータを書かない」ことを、入力バリデーション（7 章の既存データとの照合、および 3〜4 章の定型整形）で担保する。
- 既存 `data_checker.py` は本ツールとは独立に**温存**される（本ツールでは変更しない）。最終確認の安全網として引き続き手動で使える。将来的な廃止はユーザーが判断する。
- なお、単体（進化なし）を追加した場合、`data_checker.py` を実行すると「evolution_map に無い」WARN が出うる。その抑止（`data_checker_support.txt` への登録）は**本ツールの担当外**で、必要ならユーザーが従来どおり手動で行う。
- `slim_cache.json` との整合チェックも本ツールの範囲外（`slim_cache_builder.py` 実行後の別工程）。

## 9. 制約

恒久的な前提を以下にまとめる。

- **リポジトリ構成の正は `spec/repository_overview.md` とする。** 本ツール追加に伴う構成変更（`masterdata_builder/`・`src/masterdata_builder/`・`tests/masterdata_builder/` の追加、esal への書き込み関数追加）は同資料に反映する。
- **入出力はすべて `master_data/` を用いる。**
- **O/M/L 展開の正は `library.md`（`expand_targets`）とする。** 本ツールは展開ロジックを独自に持たず、確認画面の展開も `expand_targets` を呼ぶ。
- **進化マップ・図鑑・入力ファイルの形式の正は、各データファイル spec とする**（`evolution_map_spec.md`・`pokedex_numbers_spec.md` 等）。本書は形式を規定しない。
- **ファイル I/O は esal に集約する**（読み・書きとも）。features 層はファイルを直接読み書きしない。
- 依存の向きは `features → library / esal` を守る。
- 書き込みは末尾への単純追記とする（追記のみ・新規追加のみ）。
- **既存の `master_data`（3 ファイルすべて）は一切変更しない。** 既存行の上書き・修正・削除・並べ替えをしない。既存データに不整合や誤りがあっても直さず、確認画面で差分を示して人の手動チェックに委ねる（7 章）。
- ツールは値・名前・構造を生成／補完／推測しない。すべてユーザー入力に従う。
